   218→## 2. Current goals / completed modifications / verification results

   220→### New features added
   221→- **True SDK streaming** (`src/app/api/assist/route.ts`): replaced the "await full completion then chunk at 12ms/6chars" approach with `stream: true`. Now reads the SDK's `ReadableStream` with `getReader()`, parses SSE `data:` lines via a new `parseSseChunk()` helper, and forwards real model token deltas (`choices[0].delta.content`) as they arrive. Dramatically lower TTFB — first token appears as soon as the model emits it, not after the full response is generated. Includes a robust fallback: if `stream: true` fails (non-ReadableStream return or error), it falls back to a non-streaming completion + chunked typing. The `done` SSE event now includes `streamed: true/false` so the client knows which path ran.

   867→## 3. Unresolved issues / risks + next-phase priorities
   868→- **Build is simulated**: `POST /api/projects/[id]/build` waits 3s and returns a mock log — no real child process. A production deployment would spawn `bun run build` via child_process and stream stdout to the BuildRun.log. Currently no real-time streaming (could switch to SSE for live log streaming).
   869→- **File browser is a UI mock**: hardcoded tree based on project name/framework, not the user's actual filesystem (browsers can't access local FS for security). The VS Code deep-link is the real path-to-filesystem bridge.
   870→- **Connect dialogs are placeholders**: token inputs are simulated — connecting just flips the boolean flag locally without persisting an integration record to the DB. A future agent should wire these to real GitHub OAuth + Vercel OAuth + Neno API key flows that create `GitHubIntegration`/`VercelIntegration`/`NenoIntegration` rows.
   871→- **Commit/Push/Deploy are simulated**: client-side setTimeout mocks the network round-trip. Should be wired to real GitHub Commits API + Vercel Deploy API once the integrations are real.
   872→- **Optimistic UI on build**: the workspace sets `status: "ready"` immediately on POST response — but the 3s latency is server-side, so the UI shows the `building` state only briefly (the POST blocks until the build completes). A real implementation should POST to start the build (immediate 202), then poll `/api/projects/[id]/builds` for status updates. Currently the UX is acceptable because the server returns the final state.
   873→- **Env vars stored as plain JSON string keys** (no values) — production should use a secrets manager (Vault/AWS Secrets Manager).
   874→- **No real-time build log streaming** — the log is fully populated only after the build finishes. SSE/WebSocket would allow live log append.
